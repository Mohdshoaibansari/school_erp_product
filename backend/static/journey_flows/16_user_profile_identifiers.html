Flow 16 — User Profile & Identifiers Journey

← Back to all flows
This flow: Client Director manages a student's profile (create, read, update) and identifiers (student ID, admission number — create, list, delete). Covers all C-02 User Profile & Identifier endpoints not exercised by any prior flow.

All values (user IDs, tokens) come from stored env vars — nothing is hardcoded.
Prerequisites: Run Flow 1 + Flow 2 first. Stored vars required: DIRECTOR_TOKEN, CLIENT_SLUG, STUDENT_ID.

Part A — Setup

1Login as Client Director
Fresh token for profile and identifier management operations.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"$DIRECTOR_EMAIL", "password":"$DIRECTOR_PASSWORD" }

Part B — User Profile CRUD

Profile endpoints are nested under /api/v1/users/$STUDENT_ID/profile. All user IDs come from stored env vars set by Flow 2.
2Create Profile for Student
Creates a UserProfile with date_of_birth, gender, and blood_group. user_id is in the URL path from $STUDENT_ID.
POST /api/v1/users/$STUDENT_ID/profile Authorization: Bearer $DIRECTOR_TOKEN body: { "date_of_birth":"2014-07-15", "gender":"male", "blood_group":"B+" }
Expected: 201 with profile fields populated. user_id should match $STUDENT_ID.
3Get Student Profile
Read back the profile to verify it was created correctly.
GET /api/v1/users/$STUDENT_ID/profile Authorization: Bearer $DIRECTOR_TOKEN
Should show gender: "male", blood_group: "B+", date_of_birth: "2014-07-15".
4Update Student Profile
PATCH to update the blood_group from B+ to O+. Other fields remain unchanged.
PATCH /api/v1/users/$STUDENT_ID/profile Authorization: Bearer $DIRECTOR_TOKEN body: { "blood_group":"O+" }
Expected: 200 with updated blood_group: "O+". Other fields (gender, date_of_birth) preserved.
5Verify Updated Profile
GET the profile again to confirm blood_group changed to O+ and other fields are intact.
GET /api/v1/users/$STUDENT_ID/profile Authorization: Bearer $DIRECTOR_TOKEN
Should show blood_group: "O+", gender: "male", date_of_birth: "2014-07-15".

Part C — User Identifiers CRUD

Identifiers are institution-scoped business codes (Student ID, Employee ID, Admission No). Managed under /api/v1/users/$STUDENT_ID/identifiers.
6Create Student ID Identifier
Adds a student_id type identifier with a unique value. Both fields are free-text — the value is the human-readable business code (per C-12).
POST /api/v1/users/$STUDENT_ID/identifiers Authorization: Bearer $DIRECTOR_TOKEN body: { "type":"student_id", "value":"$INST_CODE-2026-001" }
Expected: 201 with type: "student_id", value: "$INST_CODE-2026-001".
7Create Admission Number Identifier
Adds a second identifier of type admission_no — separate from the student_id.
POST /api/v1/users/$STUDENT_ID/identifiers Authorization: Bearer $DIRECTOR_TOKEN body: { "type":"admission_no", "value":"ADM-2026-0042" }
8List All Student Identifiers
Should show both identifiers: student_id ($INST_CODE-2026-001) and admission_no (ADM-2026-0042).
GET /api/v1/users/$STUDENT_ID/identifiers Authorization: Bearer $DIRECTOR_TOKEN
Should list both identifiers with their IDs, types, and values.
9Delete Admission Number Identifier
Remove the admission_no identifier. identifier_id from stored var $IDENTIFIER_2_ID.
DELETE /api/v1/users/$STUDENT_ID/identifiers/$IDENTIFIER_2_ID Authorization: Bearer $DIRECTOR_TOKEN
Expected: 204 No Content — identifier deleted.
10Verify — List After Deletion
Only the student_id identifier should remain. The admission_no should be gone.
GET /api/v1/users/$STUDENT_ID/identifiers Authorization: Bearer $DIRECTOR_TOKEN
Should show only student_id: "$INST_CODE-2026-001". admission_no removed.
11Verify — Student Cannot Create Own Identifier
Student logs in and tries to create an identifier — should be blocked (no user_identifier.create permission).
POST /api/v1/users/$STUDENT_ID/identifiers Authorization: Bearer $STUDENT_TOKEN (from Flow 5 or after reset) body: { "type":"hack", "value":"fake-id" }
Expected: 403 Permission denied — Student has no user_identifier.create.
✅ Flow 16 complete. User Profile & Identifiers lifecycle verified:
  • Profile created (DOB, gender, blood_group)
  • Profile read and updated (blood_group B+ → O+)
  • Identifiers created (student_id + admission_no)
  • Identifiers listed and deleted (admission_no removed)
  • Student cannot create identifiers (403 — permission denied)
Stored: PROFILE_ID, IDENTIFIER_1_ID.
