Flow 8 — Lifecycle Gating Cross-Cutting

← Back to all flows
This flow: Tests effective-state gating — when a Client or Institution enters a non-active state, users under it should be effectively blocked from operating (D9, AC-7).
Prerequisites: Run Flow 1 + Flow 2 first. Stored vars: PLATFORM_TOKEN, DIRECTOR_TOKEN, ADMIN_TOKEN, CLIENT_ID, INST_ID.

Steps

1Platform Owner suspends the Client
Client now suspended. Institution's effective state should be gated.
2Institute Admin tries to create org unit
Should be blocked by effective-state gating (client suspended). Note: Current implementation may not enforce effective-state gating at runtime — this is logged as a known gap.
Expected (per spec): 403 effective-state blocked. Actual (current): may succeed — runtime gating is deferred (Q-AC-7 known gap).
3Reactivate the Client
4Institute Admin deactivates Institution
5Teacher tries to create homework (institution inactive)
Expected (spec): blocked by institution effective state. Actual: may succeed — runtime gating deferred.
6Reactivate Institution
✅ Flow 8 complete. Demonstrates the lifecycle gating concept.
⚠ Known Gap: Runtime effective-state gating (D9, AC-7) is not yet enforced at the API layer — a suspended Client's institution users can still operate. This is planned for a future phase. The lifecycle states themselves ARE persisted correctly, so when gating is added, it can read the state.
