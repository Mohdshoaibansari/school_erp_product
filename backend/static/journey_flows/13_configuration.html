Flow 13 — Configuration Framework (C-08)

← Back to all flows
This flow: Tests the full C-08 Configuration Framework — key registry CRUD, value overrides with scope inheritance (Platform → Client → Institution), merge strategies (append_lists), deprecation, audit log, and authorization.
Prerequisites: Backend running on http://127.0.0.1:8000. Migration 009 applied (15 seed keys). Platform Owner exists in Supabase Auth.

Part A — Key Registry

1Login as Platform Owner
No Host header — platform owner is client-independent.
POST /api/auth/login body: { "email":"admin@school-erp.com", "password":"Shoby@123" }
2List all seed keys (15 keys)
Verify the 15 seed keys from migration 009 are loaded.
GET /api/v1/config/keys Authorization: Bearer $PLATFORM_TOKEN
Should return 15 keys across 5 categories: Business Rules, Display, Academic, Notifications, Platform.
3Filter keys by category
Filter to Business Rules only — should show 4 keys.
GET /api/v1/config/keys?category=Business%20Rules Authorization: Bearer $PLATFORM_TOKEN
4Get a specific key by name
Filter by exact key name — attendance.statuses.
GET /api/v1/config/keys?key=attendance.statuses Authorization: Bearer $PLATFORM_TOKEN
Should return 1 key: attendance.statuses (json, append_lists).
5Create a new key (test.newKey)
Platform Owner creates a new string key with default value.
POST /api/v1/config/keys Authorization: Bearer $PLATFORM_TOKEN body: { "key": "test.newKey", "type": "string", "default_value": "hello-world", "category": "Platform", "description": "Test key created by journey flow" }
6Update key default value
Change default from "hello-world" to "updated-value".
PATCH /api/v1/config/keys/$NEW_KEY_ID Authorization: Bearer $PLATFORM_TOKEN body: { "default_value": "updated-value", "description": "Updated by journey flow" }

Part B — Resolution & Scope Inheritance

7Resolve key (platform default)
No scope override — should return platform default "updated-value".
GET /api/v1/config/resolve/test.newKey Authorization: Bearer $PLATFORM_TOKEN
Should return: {"key":"test.newKey", "resolved_value":"updated-value", "source_scope":"platform:default"}
8Resolve attendance.statuses (append_lists)
Should return platform default ["present","absent"].
GET /api/v1/config/resolve/attendance.statuses Authorization: Bearer $PLATFORM_TOKEN
Should return: {"resolved_value":["present","absent"], "source_scope":"platform:default"}

Part C — Value Overrides

9Create institution-scope value override
Override test.newKey at institution scope. Uses the institution from the Client Director flow (update INST_ID if needed).
POST /api/v1/config/values Authorization: Bearer $PLATFORM_TOKEN body: { "key_id": "$NEW_KEY_ID", "scope_type": "institution", "scope_id": "$INST_ID", "value": "institution-override" }
If INST_ID is not set, run Flow 2 (Client Director) first to create an institution.
10Resolve with institution scope
Should return "institution-override" (not the platform default).
GET /api/v1/config/resolve/test.newKey?institution_id=$INST_ID Authorization: Bearer $PLATFORM_TOKEN
Should return: {"resolved_value":"institution-override", "source_scope":"institution:$INST_ID"}
11Resolve without scope (should still be platform default)
No scope — the override should NOT affect the platform default.
GET /api/v1/config/resolve/test.newKey Authorization: Bearer $PLATFORM_TOKEN
Should return: {"resolved_value":"updated-value", "source_scope":"platform:default"}
12Create client-scope value override
Override test.newKey at client scope. Uses CLIENT_ID from Flow 1 or Flow 2.
POST /api/v1/config/values Authorization: Bearer $PLATFORM_TOKEN body: { "key_id": "$NEW_KEY_ID", "scope_type": "client", "scope_id": "$CLIENT_ID", "value": "client-override" }
13Resolve with client scope (should return client override)
Client scope exists — should return "client-override".
GET /api/v1/config/resolve/test.newKey?client_id=$CLIENT_ID Authorization: Bearer $PLATFORM_TOKEN
14Resolve with both scopes (institution takes precedence)
Both client and institution scopes — institution should win.
GET /api/v1/config/resolve/test.newKey?institution_id=$INST_ID&client_id=$CLIENT_ID Authorization: Bearer $PLATFORM_TOKEN
Should return: {"resolved_value":"institution-override", "source_scope":"institution:$INST_ID"}

Part D — Deprecation & Edge Cases

15Deprecate the test key
Mark test.newKey as deprecated with a replacement key.
PATCH /api/v1/config/keys/$NEW_KEY_ID Authorization: Bearer $PLATFORM_TOKEN body: { "is_deprecated": true, "replacement_key": "test.replacementKey" }
16Try to create value for deprecated key (expect 409)
Creating new overrides for deprecated keys is blocked.
POST /api/v1/config/values Authorization: Bearer $PLATFORM_TOKEN body: { "key_id": "$NEW_KEY_ID", "scope_type": "institution", "scope_id": "$INST_ID", "value": "should-fail" }
Should return 409: "Key 'test.newKey' is deprecated — cannot create new value overrides"
17Try hard delete (expect 405)
Hard delete is not supported — soft delete only via PATCH.
DELETE /api/v1/config/keys/$NEW_KEY_ID Authorization: Bearer $PLATFORM_TOKEN
Should return 405: "Hard delete is not supported."

Part E — Audit Log

18View audit log for test.newKey
Should show: key_created, key_updated, value_created (institution), value_created (client), key_deprecated.
GET /api/v1/config/audit?key=test.newKey Authorization: Bearer $PLATFORM_TOKEN
19View full audit log (all keys)
Should show all audit entries across all keys.
GET /api/v1/config/audit?page_size=10 Authorization: Bearer $PLATFORM_TOKEN

Part F — No Auth

20Access without token (expect 401/403)
Unauthenticated requests should be rejected.
GET /api/v1/config/keys (no Authorization header)
Should return 401 or 403.

Part G — Cleanup

21Delete institution override
Clean up the test.newKey institution override.
DELETE /api/v1/config/values/$INST_VALUE_ID Authorization: Bearer $PLATFORM_TOKEN
22Delete client override
Clean up the test.newKey client override.
DELETE /api/v1/config/values/$CLIENT_VALUE_ID Authorization: Bearer $PLATFORM_TOKEN
