Flow 1 — Platform Owner Onboarding

← Back to all flows
This flow: Platform Owner logs in → creates a new Client (tenant) → activates it → bootstraps the first Client Director user for that client. After this flow, you can run 02_client_director.html.
Prerequisites: Backend running on http://127.0.0.1:8000. A platform owner user exists in Supabase Auth with user_metadata.is_platform_owner = true. Run scripts/migrate_platform_owner.py if not.

Steps

1Login as Platform Owner
No Host header — platform owner is client-independent.
POST /api/auth/login body: { "email":"admin@school-erp.com", "password":"Shoby@123" }
2List all existing clients
Verify platform endpoints work. No Host header.
GET /api/v1/platform/clients Authorization: Bearer $PLATFORM_TOKEN
3Create a new Client (tenant)
Slug = subdomain that this client will use. Immutable.
POST /api/v1/platform/clients body: { "display_name":"Greenwood Academy", "legal_name":"Greenwood Academy Pvt Ltd", "slug":"greenwood", "primary_contact_email":"director@greenwood.com", "legal_entity_type_id":"a3b63601-71b4-4863-9ce5-8915d116ec60" }
New client starts in prospective state. Must be activated before users can login.
4Activate Client (prospective → active)
Required before users under this client can operate.
POST /api/v1/platform/clients/$CLIENT_ID/transition body: { "new_state":"active", "reason":"Onboarding approved" }
After success, current_lifecycle_status should be active.

Bootstrap Client Director

The first user for the new client. We create them directly via Supabase Admin API + REST API (since POST /api/v1/users needs an existing authorized user).
5Generate UUID for Director
Generate locally in JS; same UUID used for Supabase Auth + app_user.
6Create Director in Supabase Auth
Uses Supabase Admin API. Need SUPABASE_URL + SUPABASE_SERVICE_ROLE_KEY stored in env.
POST {SUPABASE_URL}/auth/v1/admin/users body: { "id":"$DIRECTOR_ID", "email":"director@greenwood.com", "password":"Director@123", "email_confirm":true }
First time? Set SUPABASE_URL and SUPABASE_SERVICE_ROLE_KEY env vars below in the store panel.
7Insert Director into app_user
No institution_id — Client Director manages the whole client.
POST {SUPABASE_URL}/rest/v1/app_user body: { "id":"$DIRECTOR_ID", "client_id":"$CLIENT_ID", "email":"director@greenwood.com", "name":"Greenwood Director", "user_category_id":"20a3b37b-56be-4573-a7ee-b2c5b016fc24", "lifecycle_status":"active" }
8Assign Client Director role
Role client_director has institution.create permission. id column needs its own UUID.
POST {SUPABASE_URL}/rest/v1/role_assignment body: { "id":"", "client_id":"$CLIENT_ID", "user_id":"$DIRECTOR_ID", "role_id":"0b542f1d-4fa3-4771-8526-af7febba2aa0", "scope":"client" }
9Verify — Director Login
Login as the new Client Director. Host = client slug + .localhost.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"director@greenwood.com", "password":"Director@123" }
Note: cross-origin Host headers set via fetch may not propagate. If login fails with subdomain not resolved, run in curl. The backend middleware will fall back to looking up client_id from app_user.
✅ Flow 1 complete. You now have:
  • PLATFORM_TOKEN — platform owner session
  • CLIENT_ID, CLIENT_SLUG — the new tenant
  • DIRECTOR_ID, DIRECTOR_TOKEN — the new Client Director
Continue to Flow 2 — Client Director.
