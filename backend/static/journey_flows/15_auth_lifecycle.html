Flow 15 — Auth Lifecycle Journey

← Back to all flows
This flow: Exercises all remaining C-03 Authentication endpoints not covered by Flow 12 — password reset (request + confirm + verify login), password change (authenticated), OTP login (request + verify), and user activation via invite token.

No hardcoded values: all user emails/passwords come from env vars set by prior flows.
Prerequisites: Run Flow 1 + Flow 2 first. Stored vars: CLIENT_SLUG, DIRECTOR_ID, STUDENT_ID. The Director and Student users must exist in Supabase Auth.

Part A — Password Reset Flow

Tests /password/reset/request → /password/reset/confirm → login with new password. In Supabase dev mode, the reset token may be returned in the API response. In production, the token arrives via email.
1Request Password Reset for Student
Triggers a password reset email for the student user. Email from stored vars — no hardcoding.
POST /api/auth/password/reset/request body: { "email":"$STUDENT_EMAIL" }
If the backend returns a token field (dev mode), it's auto-extracted to PW_RESET_TOKEN. If undefined, check Supabase dashboard → Authentication → Users → the student's email for the reset link.
2Confirm Password Reset
Uses the token from Step 1 (or paste from email). Token is substituted from env var.
POST /api/auth/password/reset/confirm body: { "token":"$PW_RESET_TOKEN", "new_password":"New$STUDENT_PASSWORD" }
If PW_RESET_TOKEN is empty: manually set it in the env panel (paste from Supabase email), then re-run this step. The old password is $STUDENT_PASSWORD.
3Verify — Login with New Password
Student logs in with the new password to confirm the reset worked.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"$STUDENT_EMAIL", "password":"New$STUDENT_PASSWORD" }
✅ Login success = reset confirmed. Expected: 200 with valid tokens.
4Verify — Old Password Rejected
Attempt login with the old password — should now fail.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"$STUDENT_EMAIL", "password":"$STUDENT_PASSWORD" }
Expected: 401 Invalid email or password — old password no longer works.

Part B — Password Change (Authenticated)

Tests /password/change — requires a valid access token. Uses the newly reset student password.
5Change Password While Authenticated
Student changes their own password from New$STUDENT_PASSWORD → Final$STUDENT_PASSWORD.
POST /api/auth/password/change Authorization: Bearer $STUDENT_NEW_TOKEN body: { "current_password":"New$STUDENT_PASSWORD", "new_password":"Final$STUDENT_PASSWORD" }
Expected: 200 {"message": "Password changed successfully"}.
6Verify — Login with Changed Password
Login with Final$STUDENT_PASSWORD — should succeed. Old New$STUDENT_PASSWORD should fail.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"$STUDENT_EMAIL", "password":"Final$STUDENT_PASSWORD" }
✅ Login with Final$STUDENT_PASSWORD = password change confirmed.

Part C — OTP Login Flow

Tests /otp/request → /otp/verify. In dev mode, the OTP may be returned in the response. In production, it arrives via email.
7Request OTP for Director
Requests an email OTP for the Client Director. Email from stored context.
POST /api/auth/otp/request body: { "email":"$DIRECTOR_EMAIL" }
If backend returns otp field (dev mode), it's stored as OTP_CODE. Otherwise check Supabase email logs.
8Verify OTP and Get Tokens
Verify the OTP (from env var or paste from email). Returns JWT tokens on success.
POST /api/auth/otp/verify body: { "email":"$DIRECTOR_EMAIL", "token":"$OTP_CODE" }
If OTP_CODE is empty: set it manually in the env panel (6-digit code from email), then re-run. Expected: 200 with access_token + refresh_token.
9Verify OTP Token Works
Use the OTP-derived token to list institutions — confirms it's a valid session.
GET /api/v1/institutions Authorization: Bearer $DIRECTOR_OTP_TOKEN
✅ OTP login verified — token can access protected resources.

Part D — User Activation (Invite Flow)

Tests /activate — accepts invite token JWT + sets password. Requires a user in invited state. When users are created via POST /api/v1/users, they start in invited state. The backend may expose an invite token for newly created users.
10Login as Director (for user creation)
Login via password to get a fresh token for creating a new invited user.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"$DIRECTOR_EMAIL", "password":"$DIRECTOR_PASSWORD" }
11Create New User (starts in invited state)
Creates a new user via the backend API. User starts in invited lifecycle status. The invite token may be returned in the response.
POST /api/v1/users Authorization: Bearer $DIRECTOR_TOKEN body: { "email":"activate-me@$INST_EMAIL_DOMAIN", "name":"Activate Test", "user_category_id":"$LOOKUP.user-categories.Learner", "institution_id":"$INST_ID" }
User created in invited state. If the backend returns invite_token or activation_url, it's auto-extracted. Otherwise check the response for invite details.
12Activate User (invite token → set password)
Accepts the invite, sets password, transitions user from invited → active. Token from $INVITE_TOKEN env var.
POST /api/auth/activate body: { "invite_token":"$INVITE_TOKEN", "password":"Activate@123" }
If INVITE_TOKEN is empty: the backend may not return invite tokens via API. Check response from Step 11 for activation details. Expected: 200 {"message":"User activated"}.
13Verify — Login as Activated User
The activated user should now be able to login with their newly set password.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"activate-me@$INST_EMAIL_DOMAIN", "password":"Activate@123" }
✅ Activation verified — user can login.
✅ Flow 15 complete. Auth lifecycle verified:
  • Password reset request → confirm → new password login → old password rejected
  • Password change (authenticated) → new password login
  • OTP request → OTP verify → OTP-derived token works
  • User activation (invite → set password → login)
⚠ Dev/production note: Password reset tokens, OTP codes, and invite tokens are normally delivered via email. In Supabase dev mode, the backend may return them in API responses (auto-extracted to env vars). If not, manually set the token from Supabase dashboard or email logs.
