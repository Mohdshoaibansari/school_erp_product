Flow 1 — Platform Owner Onboarding

← Back to all flows
This flow: Platform Owner logs in → creates a new Client (tenant) → activates it → bootstraps the first Client Director user for that client. After this flow, you can run 02_client_director.html.
Prerequisites: Backend running on http://127.0.0.1:8001. A platform owner user exists in Supabase Auth with user_metadata.is_platform_owner = true. Run scripts/migrate_platform_owner.py if not.

Steps

1Login as Platform Owner
No Host header — platform owner is client-independent.
POST /api/auth/login body: { "email":"admin@school-erp.com", "password":"Shoby@123" }
2List all existing clients
Verify platform endpoints work. No Host header.
GET /api/v1/platform/clients Authorization: Bearer $PLATFORM_TOKEN
3Create a new Client (tenant)
Slug = subdomain that this client will use. Immutable.
POST /api/v1/platform/clients body: { "display_name":"Greenwood Academy", "legal_name":"Greenwood Academy Pvt Ltd", "slug":"greenwood", "primary_contact_email":"director@greenwood.com", "legal_entity_type_id":"$LOOKUP.legal-entity-types.Pvt Ltd" }
New client starts in prospective state. Must be activated before users can login.
4Activate Client (prospective → active)
Required before users under this client can operate.
POST /api/v1/platform/clients/$CLIENT_ID/transition body: { "new_state":"active", "reason":"Onboarding approved" }
After success, current_lifecycle_status should be active.
4bFetch CLIENT_ID (if not already set)
If you already have a client (from a previous run or Step 3), this fetches its ID from the API. Skips if CLIENT_ID is already in the store.
Extracts CLIENT_ID from the client with slug greenwood. Change the slug in the extraction path if your client has a different slug.

Bootstrap Client Director (via new backend API)

A single API call replaces the old 4-step Supabase Admin workaround. The backend creates the Supabase Auth user (invited state, no password), inserts the client_user row, assigns the role, mints an invite JWT, and returns the invite URL. All lookup values resolved at runtime — no hardcoding.
5Bootstrap Client Director (single API call)
Creates Supabase Auth user + client_user row + role assignment in one shot. Returns user_id and invite_url containing the activation JWT. No SUPABASE_SERVICE_ROLE_KEY required — pure backend API.
POST /api/v1/platform/clients/$CLIENT_ID/users Authorization: Bearer $PLATFORM_TOKEN body: { "email":"director@greenwood.com", "name":"Greenwood Director", "role_id":"$LOOKUP.roles.client_director", "user_category_id":"$LOOKUP.user-categories.Executive Leadership" }
Expected: 201 with user_id, invite_url, client_id. role_id and user_category_id resolved from lookups fetched in Step 1.
6Extract Invite Token from Invite URL
The invite_url contains the JWT as a query parameter: /activate?token=<jwt>. Parse it to get the raw token needed for the activate endpoint.
The invite JWT is embedded in the URL returned by the bootstrap API. In production this URL is emailed; in dev it's returned in the API response.
7Activate Director (invite token → set password)
Director accepts the invite by setting their password. This transitions invited → active in the client_user lifecycle. Response now includes user_tier and client_slug for frontend redirect.
POST /api/auth/activate body: { "invite_token":"$INVITE_TOKEN", "password":"Director@123" }
Expected: 200 {"message":"...", "user_id":"...", "user_tier":"client_leadership", "client_slug":"greenwood"}. Frontend redirects to {client_slug}.localhost:8001/login. Tokens are obtained later via login, not here.
8Verify — Director Login
Director logs in with the password just set via activation. Host = client slug.
POST /api/auth/login Host: $CLIENT_SLUG.localhost body: { "email":"director@greenwood.com", "password":"Director@123" }
Note: cross-origin Host headers via fetch may not propagate. If login fails with subdomain not resolved, the middleware falls back to looking up client_id from the client_user table (per user_tier="client_leadership").
✅ Flow 1 complete. You now have:
  • PLATFORM_TOKEN — platform owner session
  • CLIENT_ID, CLIENT_SLUG — the new tenant
  • DIRECTOR_ID, DIRECTOR_TOKEN — the new Client Director (bootstrapped via backend API + invite activation)
All via backend APIs — zero Supabase Admin direct calls in this flow. Continue to Flow 2 — Client Director.
